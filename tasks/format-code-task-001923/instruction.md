The disk-backed segment cache is used by QueryNode to keep expensive segment data resident while indexes are refreshed in the background. `MarkItemNeedReload` currently marks a resident entry, but the next `Do` call can silently continue with stale data when the reloader fails or its context is canceled, and the marker is lost, so a transient refresh failure becomes an undetected stale-read condition. Make the public `pkg/v2/util/cache` cache lifecycle transactional around reloads.

When `MarkItemNeedReload(ctx, key)` returns true for a resident key, the next cache operation that would use that entry must attempt the configured reloader before invoking its `doer`; an entry that is not resident must return false and must not create reload state. A successful reload must atomically replace the cached value, clear the pending marker, report a cache hit (`missing == false`), and invoke the doer exactly with the replacement value. Later operations must use that replacement without reloading again until the key is marked once more.

If the reloader returns an error, `Do` must return that error (including wrapped errors) and must not invoke the doer on the stale value. The previous value must remain available and the reload marker must remain pending so a later operation can retry and recover; a failed reload must not evict or finalize the entry. Context cancellation/deadline errors from the reloader must likewise be returned through `Do`, without running the doer or clearing the marker. Keep the existing public Cache and builder surface, including the normal hit/miss result convention for resident and absent entries. Implement this without requiring callers to adopt a new API.
