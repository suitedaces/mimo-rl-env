The report UI's search box is useful for small reports, but on a large run it is difficult to combine conditions or tell whether a match came from a scenario, its container, or an HTTP call. Extend the existing `Report.testsWithStatusAndFilteredByText(status, filterText)` and `Report.httpCallsWithStatusAndFilteredByText(status, filterText)` behavior so the same filter language can be used by both report views, while keeping existing callers and ordinary searches working.

Whitespace separates clauses and every positive clause must match (AND). A double-quoted value is one value even when it contains spaces; the surrounding quotes are syntax, not part of the value. A clause may contain alternatives separated by an unquoted `|`; one alternative matching is sufficient for that clause (OR). A leading `-` makes a clause negative and excludes an entry when that clause would otherwise match. Matching is case-insensitive. Empty or whitespace-only filter text means no text restriction. Results must retain the source order.

For test entries, recognized field prefixes are `scenario:`, `container:`, and `status:` (prefix names are case-insensitive). `scenario:` examines only the scenario, `container:` examines the displayed container id, and `status:` examines the entry status; an unscoped value keeps the existing behavior of searching the scenario or container. For HTTP entries, recognized prefixes are `method:`, `url:`, `status:`, and `test:`. `method:` matches the HTTP method, `url:` matches the host-free URL shown by the report, `status:` matches the call status, and `test:` searches the owning test's scenario or container. An unscoped HTTP value keeps the existing behavior of matching a URL substring or a method prefix. A scoped method/status comparison is case-insensitive, and URL/scenario/container/test values use case-insensitive substring matching.

A field name that is not recognized in the current view is treated as a literal unscoped value, including its colon. The separate `status` argument remains an independent status filter and is intersected with the text expression exactly as before, including its existing empty/`Total` meaning. These rules must apply consistently to both public filtering methods so the navigation lists can use the richer syntax without changing their surrounding state or ordering.
