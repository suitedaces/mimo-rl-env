The dbt integration is losing relationship semantics on the way to the v1 client schema. Model dependencies are currently exported as generic edges, so downstream lineage views cannot distinguish table-level dependencies from untyped relationships; the same adapter also has inconsistent behavior for other endpoint combinations. Make the emitted DBT relationship contract complete and stable.

The v1 metadata schema must accept a `TableToTable` edge payload and expose it as `TableToTableMetadata` with `TableToTableAttributes`. When adapting a DBT relationship, choose the core edge type from the endpoint kinds, not from the relationship constraint: Table to Table is `TableToTable`, Table to Column is `TableToColumn`, and Column to Column is `ColumnToColumn`. A Column to Table relationship is not a supported directional lineage type and must remain a generic `Edge` rather than being misclassified or rejected. Every adapted edge must continue to expose the source and destination full names and namespaces supplied by its endpoints.

Preserve the integration-specific relationship metadata as well. Values supplied in a relationship metadata dictionary must be retained under the DBT metadata namespace, while the adapter-owned `definition` and `constraint_type` values take precedence over colliding user keys. Serialize `constraint_type` as the enum value used by the DBT graph (`bt` for table-to-column membership and `dbtm` for model dependencies), not the enum member name.

This must work for the integration real manifest flow as well as individual relationships: adapting the graph dependency edges must yield `TableToTable` metadata, and adapting its membership edges must still yield `TableToColumn` metadata. Keep the existing v1 node and edge payload compatibility intact.
