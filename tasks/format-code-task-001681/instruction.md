The `run` command already accepts inline task tags and can ask ECS to propagate tags from either the service or the task definition. In practice, combining these sources can send duplicate keys, let a propagated value unexpectedly override an explicit `--tags` value, and make the request depend on source order. Make task-tag assembly deterministic and validate it before invoking ECS. Parse the existing `Key=Value` list while preserving empty values and rejecting entries with an empty key. Treat tag keys as unique: when the same key occurs more than once, the later explicit value wins. When `--propagate-tags SERVICE` is selected, fetch the service tags, merge them with the explicit tags, and send one concrete deduplicated tag list to `RunTask`; explicit `--tags` values must win over service values, while service-only keys remain. The final list must be ordered lexicographically by key so repeated runs produce stable requests. Do not use ECS propagation for this mode after materializing the merged list. Preserve the existing `TASK_DEFINITION` mode by forwarding that propagation choice and leaving explicit tags intact, and preserve the empty/`NONE` modes by omitting propagation and avoiding a service-tag lookup. Any malformed inline tag must return an error before `RunTask` is called.
