The Ethereum-compatible transaction argument helpers currently disagree on how fee fields and calldata aliases are interpreted. Bring the public TransactionArgs behavior into one coherent contract so callers can safely use the same object for transaction encoding and EVM message construction.

ToTransaction must choose the legacy transaction type when neither typed fee fields nor an access list is supplied, choose the access-list type when an access list is supplied without a dynamic fee cap, and choose the EIP-1559 dynamic-fee type when either maxFeePerGas or maxPriorityFeePerGas is present. A dynamic transaction must preserve the chain ID, fee cap, and tip cap, using a zero tip when only maxFeePerGas is provided. Existing nonce, gas, gas price, value, recipient, and access-list values must remain observable in the resulting Ethereum transaction.

GetData and every conversion that uses it must prefer input over data whenever input is present, including an explicitly present empty input; data remains the backwards-compatible fallback and neither field means nil calldata. ToMessage must reject gasPrice together with either dynamic fee field using the existing error text, reject dynamic fee fields when no base fee is supplied with an error containing the London-activation message, and reject a maxFeePerGas lower than maxPriorityFeePerGas. When a base fee is supplied, effective gas price is min(maxFeePerGas, baseFee + tip); when no base fee is supplied for a legacy message, gasPrice is used unchanged. The global gas cap may reduce an omitted or oversized gas value, but an explicitly supplied zero gas value must remain zero.

Keep current public method signatures and Ethereum/Cosmos compatibility; do not require a particular internal representation.
