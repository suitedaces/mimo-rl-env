The SQL-backed model registry exposes both creation_timestamp and last_updated_timestamp, but clients cannot reliably use them for auditing: the registered-model search path rejects the documented `timestamp` sort key, and when metadata changes the parent or model-version timestamps can remain stale. Make these timestamps describe the actual lifecycle of the objects.

The public registered-model search API must accept `timestamp` and `last_updated_timestamp` in `order_by`, each with optional ASC or DESC direction. `timestamp` means the model's immutable creation timestamp; `last_updated_timestamp` means the most recent successful mutation timestamp. Both directions must sort correctly, and results must use registered-model name ascending as the deterministic tie-breaker. Paginated searches must preserve that exact ordering across every page without duplicates or omissions.

Keep each model's creation_timestamp unchanged after it is created. A registered model's last_updated_timestamp must advance when its description is updated or a registered-model tag is set or deleted. Updating a model version's description, setting or deleting one of its tags, transitioning its stage (including archiving another version), or deleting it must update that version's last_updated_timestamp and the owning registered model's last_updated_timestamp to the operation timestamp. Deleting a version must retain the existing externally visible behavior that the deleted version is no longer returned.
