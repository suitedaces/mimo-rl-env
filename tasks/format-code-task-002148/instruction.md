Subscription schedule edits need stronger validation and predictable phase timelines. The public patch protocol lets clients add and remove phases, but malformed phase patches can currently diverge from their declared path, accept unusable durations, or panic while calculating a successor shift. These failures are especially costly because a patch is applied to the subscription specification before the persisted subscription and its billing/entitlement schedules are rebuilt.

Harden the phase patch behavior while preserving chronological phase ordering. For an add-phase patch, the path phase key and the payload's phase key must identify the same phase; reject a mismatch before changing the specification. Preserve every phase-definition field supplied by the caller (start offset, display fields, sort hint, metadata) and create an empty item-history map for the new phase. If the inserted phase has a successor, its duration is required and must be strictly positive; a missing duration in that situation must return a normal error rather than panic. Appending a final phase may omit duration. Inserting a phase must move the successor and every later phase by one common delta so the new phase occupies exactly its requested duration and the relative spacing of later phases remains intact.

For a remove-phase patch, validate the shift mode as part of patch validation. Removing with the "shift next" mode must delete the selected phase and move all later phases backward by the selected phase's occupied span (the distance from its start to the next phase start), while "shift previous" must leave later phase starts unchanged so the preceding phase absorbs the gap. Unknown shift values must be rejected by validation.
