I want LARS request contexts to provide a body decoding helper with the method signature `Decode(includeFormQueryParams bool, maxMemory int64, v interface{}) (err error)` on `lars.Context` and `*lars.Ctx`. A handler should be able to receive its current request context, pass a pointer to an application struct, and have the helper choose a decoder from the request `Content-Type`, ignoring any `; charset=...` suffix.

For `Content-Type: application/json`, `Decode` should read at most `maxMemory` bytes from the request body and JSON-decode into `v`; for example a body `{"Name":"Ana"}` should populate `struct { Name string }{Name:"Ana"}` and return nil, while malformed JSON should return the JSON decoder error. For `Content-Type: application/xml`, it should likewise read at most `maxMemory` bytes and XML-decode into `v`, so `<User><Name>Ana</Name></User>` can populate a struct with a `Name` field.

For `Content-Type: application/x-www-form-urlencoded`, `Decode` should parse the submitted form and use form tags to fill struct fields. In a route like `/user/:id`, posting body `Name=Joey` to `/user/13` with `includeFormQueryParams=true` should populate `ID == 13` for `ID int `form:"id"`` and `Name == "Joey"`; with `includeFormQueryParams=false`, the same request should leave `ID == 0` while still setting `Name == "Joey"`. For `Content-Type: multipart/form-data`, the same include flag should control whether route/query values are included along with multipart value fields, and `maxMemory` should be passed to multipart parsing.

If form parsing or multipart parsing fails, `Decode` should return that parse error and not hide it. If the content type is unsupported or empty, `Decode` should return nil without decoding into the target. I also need `(*lars.LARS).BuiltInFormDecoder() *form.Decoder` to return a non-nil built-in form decoder so applications can register custom form decoding behavior before `Decode` handles URL-encoded or multipart form requests.
