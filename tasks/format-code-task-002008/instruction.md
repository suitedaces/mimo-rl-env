The HTTP Cloud Functions wrapper is currently limited to GET requests whose query string is assembled literally, and its response decoder assumes a perfectly formatted JSON content type. This makes ordinary values containing spaces or reserved characters unsafe, prevents functions that expect a JSON request body, and turns a successful response without a Content-Type header into a runtime error. Extend the public `rsf.functions.call` API while keeping existing callers source-compatible.

`functions.call(functionName, parameters = {}, options = {})` must continue to issue the legacy GET request when options are omitted: parameters are encoded as URL query key/value components in their object insertion order, and the saga yields the same fetch effect shape (URL only). The URL must retain the configured region and project id.

When `options.method` is `POST`, send the request to the function URL without a query string, JSON-stringify the parameters as the request body, and pass an init object containing `method: 'POST'` and the caller's headers. Header names are case-insensitive for determining whether a Content-Type was supplied; add `Content-Type: application/json` only when it is absent, while preserving all caller-provided header names and values.

For every successful response, inspect its Content-Type case-insensitively. Treat `application/json` with parameters and any media type whose subtype ends in `+json` as JSON and decode with `response.json()`; decode every other media type, including a missing or null header, with `response.text()`. A response whose `ok` flag is false must be thrown unchanged before any content-type lookup or decoder is attempted. The saga must return the decoded value. Existing GET behavior, region selection, and non-OK error propagation must remain compatible.
