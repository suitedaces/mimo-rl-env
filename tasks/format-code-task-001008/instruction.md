The deferrable mode of `S3KeysUnchangedSensor` is intended to be equivalent to its regular polling mode, but today the hand-off to the trigger can lose monitoring state and the asynchronous S3 check can make different decisions from the synchronous sensor. This is particularly dangerous for ingestion prefixes where one object is replaced by another: the object count does not change, but the snapshot has changed and the inactivity window must start over.

Make the deferrable sensor and its `S3KeysUnchangedTrigger` preserve the complete monitoring state across deferral and trigger serialization. The trigger must retain the bucket, prefix, inactivity period, minimum object count, previous object-key set, accumulated inactivity seconds, deletion policy, AWS connection id, and TLS verification setting, and its serialized payload must round-trip those values. The sensor's configured `poke_interval` must become the trigger's polling period and must be the delay used between trigger polls; it must not silently fall back to zero or be hidden in an unrelated hook parameter. When an asynchronous poll reports `pending`, the trigger must carry the returned object set, activity timestamp, and inactivity seconds into the next poll. `success` and `error` results must be emitted as trigger events so the sensor's existing completion/error handling remains effective.

Bring the asynchronous S3 state check into parity with the sensor's observable state machine. Compare the actual object-key sets, not just their cardinality. Any newly added key resets inactivity to zero, records the complete current set, and returns `pending`. If keys were removed, `allow_delete=True` updates the stored set, resets inactivity to zero, and returns `pending`; `allow_delete=False` returns an `error` result that identifies the monitored bucket and prefix. These rules also apply when additions and removals balance to the same total count. Only an unchanged snapshot may advance the inactivity counter and complete: once the inactivity period has elapsed and at least `min_objects` are present it returns `success`; if the period elapsed with too few objects it returns `error`. Existing non-deferrable sensor behavior and public class import paths must remain compatible.
