Secret arrays make key rotation possible, but every unsigned cookie must be checked against each secret and the signature itself gives operators no way to identify which key produced it. Add an opt-in named keyring form that produces authenticated key-ID tags while remaining able to migrate cookies created by the existing untagged format.

Expose a `SignerKeyring` with `primary: string` and `keys: Record<string, string | Buffer>`. This form must be accepted by `Signer`/`signerFactory` and by the plugin's `secret` option. Keyrings must contain at least one own key, `primary` must name one of those keys, every key ID must match `^[A-Za-z0-9_-]+$`, and every secret must remain a string or `Buffer`; reject violations with `TypeError` during signer construction. The existing algorithm argument still selects the HMAC algorithm.

For a keyring, `sign(value)` uses the primary secret and returns `<value>.<mac>~<keyId>`. Here `<mac>` is the standard base64 HMAC, with `=` padding removed, over the literal UTF-8 string `<value>.<keyId>`. This is a wire-format contract: the key ID is not URL-encoded, and values containing periods or tildes must round-trip unchanged. A valid tag from the primary key returns `{ valid: true, renew: false, value }`; a valid tag from another configured key returns the same result with `renew: true`.

When input has the tagged shape, its named key alone is authoritative. An unknown key ID, invalid key-ID syntax, malformed MAC, changed key ID, or changed MAC returns `{ valid: false, renew: false, value: null }`; tagged input must not fall back to scanning other keys. Existing untagged `<value>.<mac>` signatures are still checked against all secrets in a keyring. If any key validates one, return its original value with `valid: true` and `renew: true`, even when the validating secret is primary, because it should be reissued in the tagged format. Unverifiable legacy input keeps the normal invalid result.

Keyrings must work through the Fastify instance, request, and reply signing decorators, including `reply.setCookie(..., { signed: true })`, which must emit a tagged value using the primary key. Preserve the current behavior and wire format for string, `Buffer`, and array-based `Signer` usage and the standalone `sign`/`unsign` helpers. Objects implementing `sign` and `unsign` remain custom plugin signers and must not be interpreted as keyrings. Update the public TypeScript declarations so the exported keyring type and all accepting APIs reflect the new form and reject non-string/non-Buffer key values.
