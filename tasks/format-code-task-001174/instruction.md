Allow runtimes to consume transported Fragment results

Some XBlock runtimes execute views across a process boundary. `Fragment.to_pods()` is the natural transport format, but today its inverse cannot reliably reconstruct even a payload produced by the same class, and `Runtime.render` assumes every normal or aside view returned a live `Fragment`. This forces remote runtimes to maintain a separate, lossy adaptation layer. Make Fragment PODs a supported view-result protocol while preserving the existing in-process API.

A canonical POD contains `content`, `resources`, `js_init_fn`, `js_init_version`, and `json_init_args`. Each resource contains `kind`, `data`, `mimetype`, and `placement`. A Fragment must survive `to_pods()`, JSON encoding/decoding, and `from_pods()` with the same body, head and foot HTML, resource order, initializer name/version, and initializer arguments. Explicit falsey initializer arguments (`{}`, `[]`, `0`, `False`, and the empty string) are values and must not be collapsed to `None`. For compatibility, `from_pods()` must accept legacy payloads that omit `json_init_args`, treating it as `None`, and must ignore unknown members both on the top-level payload and on individual resource records.

POD conversion is a transport boundary: neither `from_pods()` nor `to_pods()` may share nested mutable initializer data or resource records with the caller. Mutating the source payload after import, or mutating a payload returned by `to_pods()`, must not change the Fragment. Reject a non-dictionary payload, a payload missing any required canonical member other than the legacy-optional `json_init_args`, or a resource missing one of its four required members with `TypeError` or `ValueError`; do not expose incidental `KeyError` or `AttributeError` failures.

`Runtime.render` must accept either a live `Fragment` or a valid Fragment POD from a named view and from `fallback_view`. Aside view functions must support the same two result forms. Once rendered, transported results must behave like native Fragments: content is wrapped normally, head and foot resources are retained, JavaScript initializer metadata and JSON arguments appear in the normal wrapper output, and resources from transported asides are merged into the final result. Field changes made by a successfully rendered primary view must still be saved. If a primary view returns a malformed POD, rendering must raise `TypeError` or `ValueError` and changes made during that failed view invocation must not be persisted. Existing normal, fallback, and aside views that return live `Fragment` objects must continue to work unchanged.
