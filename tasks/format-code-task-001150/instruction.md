The Python client currently can only upload files that fit in one request, which makes it unusable for large files and impossible to resume an interrupted transfer. Extend the public `GirderClient.uploadFileToItem` workflow so callers can upload arbitrary local files through the existing Girder file-upload protocol without losing the convenience of the current method.

A normal call with an item id and a local path must initialize an upload using the file's basename and exact byte size, then send the complete file as one or more binary chunks no larger than the client's configured `MAX_CHUNK_SIZE`. Each chunk must carry the current acknowledged offset, starting at zero for a new upload, and the method must continue until the server reports the final file object; intermediate responses are not final results. A zero-byte initialization is already complete and must return the file object without posting a chunk.

Support resuming an existing upload when the optional `uploadId` argument is supplied. In that mode do not create a second upload record; query the server's current offset, skip exactly that many source bytes, and append only the remaining bytes with matching offsets. Reject an offset beyond the local file size rather than silently completing or sending invalid data. Preserve arbitrary binary bytes and use the local basename even when the path contains directories.

Successful completion returns the final response object's `_id`. A non-success chunk response, malformed or incomplete initialization/final response, or impossible resume offset must raise an exception that identifies the failed request instead of being treated as success. Existing callers that omit `uploadId` retain the same return value and request shape for files that fit in one chunk.
