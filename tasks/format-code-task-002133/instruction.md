Harden libcontainer's user-namespace ID mapping handling so malformed maps are rejected before they can reach the kernel or produce a wrapped host ID. Today the public configuration validator largely checks only whether mappings accompany a user namespace, while the HostUID/HostGID helpers perform arithmetic directly on int values. Overlapping or overflowing ranges can therefore be ambiguous or translate to a negative host ID.

Treat each UID and GID mapping as a half-open pair of ranges: [ContainerID, ContainerID+Size) maps to [HostID, HostID+Size). When a config contains NEWUSER, both the UID and GID mapping lists must be non-empty and each must map container ID 0. Every entry must have non-negative starts and a positive size. Both endpoints must be computable without native-int overflow and must remain in Linux's usable 32-bit ID space: ID 4294967295 is the unmapped sentinel and may not be a start or be included in a range; 4294967294 is legal when represented by the current platform.

Within one UID list or one GID list, reject overlaps in either container-ID space or host-ID space, including exact duplicates. Input order is not significant and adjacent ranges are valid. UID and GID maps are independent, so they may use identical numeric ranges.

Apply the same safety rules to Config.HostUID and Config.HostGID. With NEWUSER enabled, they must translate every mapped boundary correctly, reject negative and unmapped container IDs, and return an error rather than selecting from an ambiguous map or returning an overflowed host ID. With no NEWUSER namespace, retain the existing identity translation behavior; mapping data without NEWUSER remains invalid at configuration validation.

Rootless mount-option checks must use the complete validated mapping lists. A uid= or gid= value at the last ID of any mapping is accepted, while the immediately following unmapped ID is rejected, regardless of mapping order. Preserve existing behavior for ordinary valid single-range configurations.
