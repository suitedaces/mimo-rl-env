Local `CaseSuite` execution currently walks cases in insertion order, so a consumer can run before the case that produces its inputs. Failures are logged but do not prevent dependent work from running, disabled cases are still invoked, and callers (including `run-suite`) cannot tell whether the suite completed successfully. Make local suite execution dependency-aware and expose a deterministic result without changing how `Case.dependencies` are discovered.

Change the public API to `CaseSuite.run(failFast=False)`. Before invoking any case, resolve the suite's dependency graph. A dependency that is not a member of the suite must raise `ValueError` before any case runs, and the message must identify both the dependent case and the missing dependency. A cycle must likewise raise `ValueError` before execution and identify the cases in the detected cycle. Existing explicit dependencies, `reloadDBName`/`loadStyle` dependencies, and `explicitRepeatShuffles` dependencies must continue to be recognized.

Run an enabled case only after all of its dependencies have succeeded. Whenever several cases are runnable, select the one that was inserted earliest in the suite; this makes execution deterministic while still allowing a parent inserted after its child to run first. Each case must execute from its own `case.directory`, and the caller's working directory must be restored after both successful and failed case runs.

Return a dictionary containing every suite `Case` object as a key. Use the exact status strings `succeeded`, `failed`, `blocked`, `disabled`, and, when applicable, `cancelled`. A disabled case is not invoked and receives `disabled`; any enabled case that directly or transitively depends on a disabled, failed, or blocked case is not invoked and receives `blocked`. Exceptions from `Case.run()` remain contained by the suite and mark that case `failed`. With the default `failFast=False`, unrelated runnable cases continue after a failure.

With `failFast=True`, stop invoking cases after the first execution failure. Preserve causal statuses: transitive dependents of an unsuccessful case are `blocked`, cases disabled from the outset remain `disabled`, and other enabled cases that had not run are `cancelled`.

Finally, make the `run-suite` command reflect this result in its public exit code: return `0` when all outcomes are only `succeeded` or `disabled`, and return `1` if any outcome is `failed`, `blocked`, or `cancelled`.
