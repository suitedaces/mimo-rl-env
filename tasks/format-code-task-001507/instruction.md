Service handlers can currently signal only success or failure, which forces integrations that calculate useful data to publish it through unrelated state or event channels. Add an opt-in structured response path while keeping existing fire-and-forget services fully compatible.

Define a public string-valued `SupportsResponse` enum in `homeassistant.core` with exactly `NONE = "none"`, `OPTIONAL = "optional"`, and `ONLY = "only"`, plus a public `ServiceValidationError` in `homeassistant.exceptions` that derives from `HomeAssistantError`. Extend `ServiceRegistry.async_register` with a `supports_response` option. It defaults to `SupportsResponse.NONE`, and the selected value must be visible on the corresponding service object returned by `async_services()`.

Extend `ServiceRegistry.async_call` with `return_response=False`. A requested response is valid only for a blocking call: `return_response=True` with `blocking=False` must raise `ValueError` whose message identifies the response/blocking conflict. `NONE` services reject response requests, and `ONLY` services reject calls that do not request a response. Those capability mismatches raise `ServiceValidationError` with a message that identifies the fully qualified service and explains the response mismatch. All of these validations happen before the `call_service` event is fired and before the handler runs.

When a response is requested from an `OPTIONAL` or `ONLY` service, return the handler's JSON-compatible dictionary unchanged. This must work for coroutine handlers, event-loop callbacks, and ordinary synchronous handlers run by the executor. When an optional response is not requested, preserve the existing results: a completed blocking call returns `True`, and a nonblocking call returns `None` while still scheduling the handler, even if that handler produces a dictionary. Preserve existing exception behavior as well: blocking handler exceptions propagate, while nonblocking exceptions remain background failures.

Expose the live capability in every result from `async_get_all_descriptions()` as `supports_response` using the enum's string value. This metadata must follow re-registration of the same service instead of becoming stale, while cached name, description, fields, and target documentation remain intact.

Finally, extend the WebSocket `call_service` command with an optional strict boolean `return_response` field. When true, make the blocking core call with response return enabled and send a successful result containing both the existing serialized `context` and a `response` member with the returned dictionary. When omitted or false, retain the context-only result shape with no `response` key. Capability validation must use the normal failed-result envelope with code `home_assistant_error`, an explanatory response message, and no handler execution; non-boolean flags must be rejected as `invalid_format`.
