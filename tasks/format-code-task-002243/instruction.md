The dashboard's GET /serverInfo response is assembled from the feature registry, but the registry currently drops adapter-provided metadata and treats legitimate configuration values as if they were disabled. It also exposes mutable references, so a consumer can silently change later responses. Make the registry's public contract explicit while keeping existing feature consumers compatible.

The module must continue to expose setFeature(key, value) and getFeatures(), and add setFeatureSwitch(key, enabled) for independently controlling visibility. Every key registered with setFeature is visible from getFeatures() by default, including keys that were not present in the initial built-in switch table (for example the server version set during server construction). Built-in feature groups that are enabled today remain enabled by default. A switch set before registration must apply when the key is later registered; changing a switch must hide or reveal the current value without deleting it, and replacing a value must not reset that switch.

Feature values are JSON-compatible data. Their value is the exact value supplied, including false, 0, null, and an empty object; truthiness must never decide whether an enabled key is returned. Calling setFeature replaces the previous value for that key rather than shallow-merging it. The registry must own its data: later mutation of an object or array passed to setFeature must not change the registry, and mutating an object returned by getFeatures must not change a subsequent snapshot. getFeatures() may return a fresh deep snapshot on every call.

setFeatureSwitch accepts only a boolean enabled argument and must synchronously throw a TypeError for other types; it must not partially change the switch in that case. Preserve the existing CommonJS exports and the behavior of existing callers that only set and read feature groups.
