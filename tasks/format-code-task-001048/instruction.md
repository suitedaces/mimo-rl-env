Dynamic configuration is used for both global defaults and progressively narrower namespace/task-queue/task-type overrides, but the current lookup path treats a rule as matching only when its constraint map has exactly the same keys as the caller. That makes a namespace or namespace+queue override disappear whenever a caller also supplies task type, and the Collection convenience getters can mistake a broader value for a hit. It also makes an explicitly configured zero-like value indistinguishable from a miss. Make constraint resolution consistent for direct clients and Collection task-queue accessors.

A configured constrained value matches when every constraint on that value is present in the requested filters with the same canonical value; additional requested filters must not disqualify it. Among matching constrained values, select the one with the greatest number of constraints. If multiple matching values have equal specificity, retain declaration order and use the first one. If no constrained value matches, use the configured unconstrained default, or the caller-supplied default when no value is configured, and preserve the existing missing-key error behavior. Unknown extra filter keys must not prevent a known constraint from matching.

The task-queue Collection getters for int, float, duration, and bool must observe that same most-specific precedence, including when the selected value is equal to the getter's default (0, 0.0, false, or a zero duration). A value created with `ForTaskType` must interoperate with the task-type representation produced by `TaskTypeFilter`, so a workflow/activity override is selectable through the public Collection API.
