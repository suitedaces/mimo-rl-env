Picard currently flattens all recording-to-work relationships into one metadata object and then applies the instrumental rule globally. This breaks medleys: an instrumental section can erase the language and lyricist credits belonging to other works performed in the same recording. Make recording metadata import relationship-aware while preserving the existing public tags and compatibility behavior.

When importing a recording through the existing MusicBrainz JSON metadata path, process each `performance` relationship to a work independently. A work relationship whose attributes include `instrumental` must not contribute that work's language or lyricist credits. Non-instrumental performance relationships, including relationships with no `attributes` member and a second performance of the same work, must contribute their work language(s), work title and ID, and nested artist roles as usual. Instrumental attributes must still be exposed in `~performance_attributes`.

The final recording-level tags should represent the aggregate of the contributing works: if at least one non-instrumental work supplies a language, retain those language values and lyricist credits even when another work is instrumental; do not replace them with `zxx` or remove them merely because an instrumental relationship exists. If every performance relationship is instrumental, retain the established no-lyrics behavior (`language` is `zxx` and `lyricist` is absent). Relationships of other types must not trigger instrumental suppression. Existing recording fields, work IDs/titles, role mapping, and handling of ordinary payloads must remain compatible.
