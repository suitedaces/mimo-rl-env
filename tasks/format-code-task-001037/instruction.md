The Tika client used by Paperless has changed its response wrappers over time. The office-document parser and the email parser currently make different assumptions about where extracted fields live, so an upgrade can turn a successful parse into an AttributeError or a lost creation date. Make both Tika-backed paths consume the modern response object while retaining compatibility with the legacy nested form.

For office documents, `TikaDocumentParser.parse` must trim textual content and expose it through the parser's normal getters. It must read a creation timestamp from the modern top-level response field, while still accepting the legacy `metadata.created` field. Missing or null content is a valid empty result (`""`), and a missing or malformed creation timestamp must leave the date unset rather than aborting parsing. A successful parse must continue through PDF conversion and expose the converter's archive path. Failures raised while requesting Tika must remain `ParseError` failures that identify the configured endpoint and retain the original exception as the cause.

Metadata extraction must accept either the client's response object (`.data`) or a plain mapping and emit the same one-record-per-key metadata entries, preserving each key and value and the mapping's iteration order. Email HTML extraction via `MailDocumentParser.tika_parse` must use the same content normalization: trim a present content value, return `""` when it is absent, and keep its existing `ParseError` boundary for request failures. Keep existing public parser getters, conversion behavior, and legacy responses working.
