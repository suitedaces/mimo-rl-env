Octant's YAML apply path currently starts creating resources while it is still decoding the input stream, and it submits a Kubernetes `List` wrapper as though the wrapper were a resource. That makes a malformed later document leave an avoidable partial apply and prevents manifests emitted as generic lists from working. Add a preflight phase to `CreateOrUpdateFromHandler` (and therefore `CreateOrUpdateFromYAML`) while retaining the established per-resource apply behavior.

Decode and normalize the entire YAML/JSON stream before the first object lookup, create, or dynamic patch. Ignore empty YAML documents. A generic object whose `kind` is `List` is a container, not an apply target: recursively expand its `items` depth-first at its position in the stream. `items` must be an array and every item must be an object; an empty list is valid and produces no work. Every concrete resource must have non-empty `apiVersion`, `kind`, and `metadata.name`.

Treat the namespace argument as an apply boundary. A concrete resource may omit `metadata.namespace` or explicitly use that same namespace, but a different explicit namespace rejects the request. Reject duplicate concrete identities across documents and expanded lists; identity is the case-sensitive tuple of apiVersion, kind, effective namespace, and name, with an omitted namespace treated as the requested namespace for this preflight comparison. Any parse, list-shape, required-field, namespace, or duplicate error anywhere in the input must return an error with no result messages and without invoking object lookup or mutation for any resource.

After preflight succeeds, apply the flattened resources in stream order using the existing discovery-driven scope behavior. Default an omitted namespace only for namespaced resources; an omitted namespace on a cluster-scoped resource must remain empty, while an explicit matching namespace is preserved. Continue to choose create when lookup reports NotFound and server-side apply when it finds an object. Preserve the existing result text (`Created` or `Updated`, kind, API version, name, and `in <namespace>` only for namespaced resources) in flattened apply order. This preflight is not a transaction: if lookup, discovery, create, or patch fails after execution begins, stop at that resource, wrap and return the underlying error, and return the successful result messages accumulated before it.
