I want `ParallelImportBuilder` to support VMF map jobs in the same queued workflow as the other asset types. The builder should accept VMF-specific keyword options on construction: `vmf_import_lights`, `vmf_light_factor`, `vmf_sun_factor`, `vmf_ambient_factor`, `vmf_import_sky_camera`, `vmf_sky_equi_height`, `vmf_import_unknown_entities`, `vmf_import_brushes`, `vmf_import_overlays`, `vmf_epsilon`, `vmf_cut_threshold`, `vmf_merge_solids`, `vmf_invisible_solids`, `vmf_import_props`, `vmf_import_entities`, `vmf_import_sky`, `vmf_scale`, plus optional VMF output collections `vmf_brush_collection`, `vmf_overlay_collection`, `vmf_prop_collection`, `vmf_light_collection`, and `vmf_entity_collection`.

The public method should be `add_vmf(path: str, from_game: bool = True) -> ParallelImportBuilder`. Calling it should append one VMF job, return the same builder for chaining, and increase `job_count` by one; for example, `builder.add_vmf("maps/de_dust2.vmf").add_mdl("models/props_crates/static_crate.mdl")` should leave two queued jobs before `execute()`.

When `execute(context=None) -> None` runs, each VMF job should be passed to the native queued importer with its path and `from_game` flag. A VMF job loaded with `from_game=True` should resolve the path through the game file system, while `from_game=False` should treat the path as a local OS path. The VMF options from the builder constructor should control the queued map import: brush and overlay geometry settings, prop import, other entity import, sky import, scale, lighting factors, sky camera import, unknown entity empties, and target Blender collections for the generated map assets.

If a queued VMF file cannot be read or parsed, `execute()` should log the VMF failure and continue the batch instead of raising an `AssetImportError` for the whole parallel import. After `execute()` completes, the builder should clear the queued jobs so `job_count` returns to zero.
