Progress task telemetry is currently hard to trust when callers mix `advance` and absolute `completed` updates: the public rate and ETA can drift, corrections can contaminate the estimate, and changing a task's lifecycle leaves stale measurements behind. Make the `Progress`/`Task` public behavior coherent. Every positive completion delta, whether supplied through `advance` or `update(completed=...)`, must contribute to one rate estimate over the configured sampling window; zero or negative deltas must update the visible completed value but must not add rate evidence. `Task.speed` should report completed steps divided by elapsed time between the retained samples, and `Task.time_remaining` should use that rate and ceil the remaining work (while retaining the existing `None` behavior when no estimate is possible). Reaching a finite total through `update` must mark the task finished and capture the speed at that moment; later updates must not change `finished_time` or `finished_speed`. Calling `reset` must clear all old rate evidence, retain the task total, and permit a fresh estimate from later samples. Changing `total` through `update` must invalidate the old rate evidence. Existing task IDs, descriptions, visibility, fields, rendering, and the behavior of indeterminate (`total=None`) tasks must remain compatible.
