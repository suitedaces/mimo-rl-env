Storage drivers are long-lived objects backed by authenticated sessions, but their ownership is currently implicit. Replacing or removing an entry from the driver cache only changes the dictionary, and a temporary driver created during registration or an access-info update is leaked whenever a later validation or database operation fails. Please make driver shutdown explicit and make those ownership transitions failure-safe.

Add a public `close()` lifecycle operation to the storage-driver contract. The base implementation must be a backward-compatible, repeatable no-op so existing third-party drivers do not become abstract or need an immediate implementation. VMAX and OceanStor must provide real, idempotent cleanup: closing an active VMAX driver closes its PyU4V session once, and closing an active OceanStor driver logs its REST session out once. Calling either driver's `close()` again must not contact the backend again. Keep VMAX's existing best-effort cleanup when an unclosed object is destroyed.

The driver manager owns every object in its cache. Adding a driver under a previously unused storage ID leaves it open. Updating an ID with the exact same object is also a no-op. Updating it with a different object installs the replacement and closes the displaced driver exactly once. Removing an existing ID evicts and closes that driver exactly once; removing an unknown or already removed ID does nothing. Shutdown is best-effort at this boundary: an exception raised by `close()` must not escape, and must not undo the requested replacement or eviction.

Registration and access-info update create uncached candidate drivers before they validate or persist anything. Ownership transfers to the manager only after the workflow succeeds. On success, preserve the existing return values and validation behavior, cache the candidate, and leave that candidate open. If any step after candidate creation fails, including backend discovery, storage consistency/repetition validation, or access/storage persistence, close the candidate once and do not cache it. Cleanup failure must never replace or mask the original workflow exception; callers must receive the same original exception object. Existing successful discovery, access update, cache removal, and their established validation errors must remain compatible.
