I want ants to expose load-balanced multi-pool objects so a Go caller can shard task dispatch across several underlying goroutine pools through one stateful handle. The API should include `type LoadBalancingStrategy int` with `RoundRobin` and `LeastTasks`, `NewMultiPool(size int, sizePerPool int, lbs LoadBalancingStrategy, options ...Option) (*MultiPool, error)`, `NewMultiPoolWithFunc(size int, sizePerPool int, fn func(any), lbs LoadBalancingStrategy, options ...Option) (*MultiPoolWithFunc, error)`, and `NewMultiPoolWithFuncGeneric[T any](size int, sizePerPool int, fn func(T), lbs LoadBalancingStrategy, options ...Option) (*MultiPoolWithFuncGeneric[T], error)`. Creating one with `size <= 0` should return `ErrInvalidMultiPoolSize`; using a load-balancing strategy other than `RoundRobin` or `LeastTasks` should return `ErrInvalidLoadBalancingStrategy`; option validation errors from the underlying pools, such as invalid expiry duration, should be returned too.

For a raw multi-pool, callers should be able to run `mp, err := ants.NewMultiPool(10, 5, ants.RoundRobin)`, call `mp.Submit(func(){ ... })` repeatedly, inspect `mp.Running()`, `mp.Free()`, `mp.Waiting()`, and `mp.Cap()`, and then close it with `mp.ReleaseTimeout(timeout)` or `mp.ReleaseContext(ctx)`. With 10 pools of capacity 5 and 50 long-running submitted tasks, `Running()` should report 50, `Free()` should report 0, `Waiting()` should report 0, and `Cap()` should report 50. The per-pool methods `RunningByIndex(idx int) (int, error)`, `FreeByIndex(idx int) (int, error)`, and `WaitingByIndex(idx int) (int, error)` should report the selected underlying pool's counts and return `ErrInvalidPoolIndex` for negative indexes or indexes outside the pool list.

Dispatch should honor both balancing modes. `RoundRobin` should rotate submissions across the pool list and, if a selected pool reports overload, retry the submission on the least-busy pool; `LeastTasks` should choose the pool with the fewest running tasks for each submission. `MultiPoolWithFunc` should provide the same lifecycle and metrics around `Invoke(args any) error`, and `MultiPoolWithFuncGeneric[T]` should provide the same behavior around `Invoke(args T) error`.

Closing a multi-pool should close every underlying pool as one unit. `IsClosed() bool` should flip to true after release, a second release should return `ErrPoolClosed`, and `Submit` or `Invoke` after closure should return `ErrPoolClosed`. `ReleaseContext(ctx)` should wait for all underlying pools to close, return an error if the context is canceled before completion, and include the pool index in any per-pool release error it reports. `Reboot()` should reopen a released multi-pool and reset dispatch so new submissions or invocations work again. `Tune(size int)` should resize each underlying pool to the given per-pool capacity while keeping the number of pools unchanged.
