I want the library's GraphQL document builder to add aggregate count selections for list-style reads so React Admin list responses can include a total row count.

The public API I need is an exported `buildMetaArgs(query: IntrospectionField, variables: any, aorFetchType: FetchType): ArgumentNode[]` helper, and `buildGqlQuery(introspectionResults, buildFields, buildMetaArgs, buildArgs, buildApolloArgs, aggregateFieldName)(resource, aorFetchType, queryType, variables)` should return a GraphQL AST document deterministically without mutating its inputs.

For `GET_LIST`, `GET_MANY`, and `GET_MANY_REFERENCE`, the returned document should contain the normal `items` field plus a top-level field aliased as `total`; by default that field name is `${queryType.name}_aggregate` and its selection is `aggregate { count }`. For example, with query field `person`, scalar fields `id`, `name`, and variables `{ limit: 5, offset: 0, order_by: ..., where: ... }`, a `GET_LIST` document should include `total: person_aggregate(order_by: $order_by, where: $where) { aggregate { count } }`.

The aggregate count field should use `buildMetaArgs`, which includes defined matching query arguments but, for those list-style fetch types, omits pagination args `limit` and `offset`; it should also skip undefined args. If `aggregateFieldName('person')` returns `person_stats`, the same `GET_LIST` selection should be `total: person_stats(...) { aggregate { count } }`. If `aggregateFieldName(...)` returns the public sentinel string `NO_COUNT`, the list-style document should omit the `total` aggregate selection entirely.

The default `buildQuery` and data provider path should use `resourceName => resourceName + '_aggregate'` unless the user supplies `buildGqlQueryOverrides.aggregateFieldName`, and `buildGqlQueryOverrides.buildMetaArgs` should allow a custom aggregate argument builder. Calling the builder twice with the same inputs should produce equal ASTs and should not write to the filesystem, network, globals, or mutate the variables object.
