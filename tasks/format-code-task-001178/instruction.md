The system information endpoint currently parses `dmidecode` output with state that can leak from one hardware handle into the next. On machines with multiple memory-array records it may report ECC incorrectly, and an `I2C Slave Address` line outside an IPMI (DMI type 38) record can falsely claim that IPMI hardware exists. This makes hardware capability reporting unreliable in diagnostics and UI consumers.

Correct the DMI information behavior exposed by `SystemService.dmidecode_info()`. Parse each `dmidecode` handle according to its DMI type: manufacturer/product fields from type 1 belong to system fields, those from type 2 belong to baseboard fields, release dates come from type 0, and the IPMI flag is set only by an I2C address in type 38. Values from unrelated types must not overwrite those fields. Treat the memory-array records (type 16) as a collection: `ecc-memory` is true when any record reports an error-correction value containing `ECC`, and false when no memory record does. Missing records retain the existing empty-string/false defaults.

Accept both two-digit and four-digit `MM/DD/YY` or `MM/DD/YYYY` BIOS dates as `datetime.date` values. Malformed or incomplete dates must leave the date field at its empty default and must not make the query fail. Preserve the existing cache keys and return shape, and continue to tolerate section headers or records that omit optional fields.
