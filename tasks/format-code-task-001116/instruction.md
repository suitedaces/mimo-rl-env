Extend Ecto.Multi with first-class read operations so a transaction can inspect data as part of the same ordered workflow as writes. Add public all/4, one/4, and exists?/4 operations taking the multi, an operation name, an Ecto.Queryable, and an optional keyword-list of repository options. Each operation must be introspectable through Ecto.Multi.to_list/1 using its own canonical tuple shape and must participate in the existing unique-name validation. When executed through Repo.transaction/1, all returns the query result list, one returns nil for no rows or the single value for exactly one row and raises Ecto.MultipleResultsError for multiple rows, and exists? returns a boolean while applying the repository's normal existence-query semantics (including a one-row limit and selecting a constant). Options supplied to an operation must be retained in its canonical representation, and options such as prefix must be forwarded to the underlying repository call. Read results must be inserted into the changes map under their names, preserve the order in which operations were added, and be available to later run callbacks. A prior error must stop subsequent read operations and return the same {:error, failed_name, reason, changes_so_far} transaction shape already used by Ecto.Multi. Keep existing write, run, merge, append, prepend, and to_list behavior compatible.
