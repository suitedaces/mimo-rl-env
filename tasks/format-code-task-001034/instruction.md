The EVM keeper's transaction log path is losing information needed by Ethereum clients. The transient bloom accumulator and transaction index currently share state, and logs written during execution do not consistently carry their block location or make the block bloom useful to RPC filters. Repair this lifecycle while keeping the existing keeper and query APIs compatible.\n\nFor the transient per-block state, the bloom value and transaction index must be independent. Reading the index before any transaction has advanced it returns zero; advancing it repeatedly yields 1, 2, ... without changing the previously stored bloom, and writing/reading bloom state must not panic or reinterpret index bytes. The transient state remains scoped to the current block as intended by the existing BeginBlock/EndBlock lifecycle.\n\nWhen a log is added for a transaction context containing encoded Ethereum transaction bytes, the persisted log must identify that transaction, the current block height, and the current block header hash. It must use the current transaction index for every log from that transaction. Multiple logs for one transaction are retained in append order and receive consecutive zero-based log indexes, while their topic and data payloads remain intact.\n\nEvery emitted log must also contribute its address and each topic to the current block bloom. Contributions from multiple logs are cumulative, and EndBlock must persist the accumulated bloom at the block height so the existing BlockBloom query and RPC filter path can observe all of them. Empty blocks continue to produce a valid zero bloom, and unrelated log/query behavior must remain compatible.
