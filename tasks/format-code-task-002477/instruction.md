I want a stateful `WriteAheadLog` class for applying Raiden state changes durably and atomically. It should be constructed as `WriteAheadLog(state, storage, state_transition)`, keep the current state in the instance, expose `get_current_state() -> State`, and expose a read-only `version` property that returns `storage.get_version()`. If `state_transition` is not callable, construction should raise `ValueError`.

I need to process one or more state changes with `with wal.process_state_change_atomically() as dispatcher:`. Inside that context, `dispatcher.dispatch(state_change) -> List[Event]` should apply `state_transition` to the current working state, return the emitted events, serialize and write the state change to the WAL, and serialize and write each emitted event linked to that state change in the same database transaction. `dispatcher.latest_state()` should return the working state after the state changes already dispatched in that same context, so a later state change in the batch can be derived from the updated state.

The WAL must not mutate the previously committed state while a batch is still open: it should process the batch on a deep copy and only replace `wal.get_current_state()` when the context exits successfully. If an exception aborts the context after some dispatches, neither the copied state nor the partially written state changes/events should become committed observable WAL state. After at least one state change is dispatched successfully, `wal.saved_state` should be a `SavedState` value that keeps the committed state together with the identifier of the last written state change.

I also need `wal.snapshot(statechange_qty: int) -> None` to persist a snapshot of the current WAL state using the last successfully written state-change identifier and the supplied count. For example, after dispatching two state changes that move a toy counter state from `0` to `2`, `get_current_state()` should return the counter state `2`, both state changes and their events should be readable from storage, and `snapshot(2)` should write a snapshot for that counter state at the second state-change id.
