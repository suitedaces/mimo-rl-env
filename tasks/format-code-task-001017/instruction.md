Extend the shared Redis connection options so the collection can use mutual TLS without forcing callers to replace these modules with custom code. The affected public modules are `community.general.redis`, `redis_info`, `redis_data`, `redis_data_info`, and `redis_data_incr`, all of which should accept the same client-certificate profile.

Add `client_cert_file` and `client_key_file` for the PEM client certificate and private key, plus `client_key_password` for an encrypted private key. When TLS is enabled and a complete profile is supplied, pass those values to redis-py as its client certificate, key, and key-password connection settings. Do not emit client-certificate settings when no profile was requested, and do not pass a password merely because the option is absent.

Reject an incomplete profile: certificate and key must be supplied together, a key password requires a key, and any client-profile option requires `tls: true`. These failures must happen at module argument/connection setup time and identify the relevant option names. Existing behavior remains compatible: the modules keep their current TLS defaults (`redis` and `redis_info` disabled by default, the data modules enabled), an enabled TLS connection without `ca_certs` still uses certifi, `validate_certs` retains its current effect, and username/password authentication continues to be forwarded unchanged.

Keep the option set consistent across all five modules and their shared Redis documentation so a playbook can move between information and mutation modules without changing its connection profile.
