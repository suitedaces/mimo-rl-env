The search layer's DSL helpers are used by resource and concept queries, but several option-handling bugs make valid requests produce the wrong Elasticsearch body. Please make the public builders compose deterministic, usable DSL while preserving the existing fluent API.

`Query.add_filter` must accept only the boolean operators `and` and `or` (case-sensitive); an invalid operator is a `ValueError`. Multiple filters are retained in insertion order and wrapped under the selected operator, while the query clause remains intact. Omitting the operator keeps the existing default of `and`. `Query.search` must prepare and pass the complete body to the search engine, including explicit zero values for `start`/`limit` and an explicitly supplied empty `fields` list.

`Bool.merge` must merge, rather than overwrite, each of the `must`, `should`, and `must_not` collections. `Terms` continues to accept either one term or a list and exposes a list in the resulting DSL. `Range` rejects conflicting lower bounds (`gte` with `gt`) or conflicting upper bounds (`lte` with `lt`), requires at least one bound, and preserves an explicitly supplied `boost=0` as well as bound value zero.

`Match` must preserve an explicitly supplied `fuzziness=0`. `SimpleQueryString` must emit the Elasticsearch `simple_query_string` clause (not a prefix query), support either a single field or a list of fields, and include the requested `query`, `default_operator`, `analyzer`, and `flags` values. These changes are about the observable DSL and execution request; do not require callers to change their current constructor or search invocation style.
