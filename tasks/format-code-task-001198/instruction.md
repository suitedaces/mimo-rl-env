Custom profiles routinely build on several other profiles, but today `include_profiles` behaves like a check-list copy rather than true profile composition: inherited configuration defaults and status policies disappear, duplicate checks can run more than once when they came from different sections, and a bad include graph ends in an opaque recursion failure. Please make compiled profiles compose all of this policy predictably.

Process included profiles depth-first in the order listed, followed by the including profile's own declarations. Configuration defaults must be inherited transitively and merged at the check-ID and variable-name levels, so an override of one variable does not discard sibling variables. For conflicts, a later included profile wins over an earlier one, and the including profile wins over every include. When a user supplies a check-specific configuration namespace at runtime, merge it over the compiled profile defaults by variable name as well; omitted variables keep their defaults, while explicitly supplied falsy values such as `0` remain real overrides. Other top-level runtime configuration and the existing explicit/excluded-check selection behavior must continue to work.

Status overrides must compose transitively too. Merge rules by check ID and message code: preserve rules for unmentioned codes, replace an earlier rule when a later include defines the same code, and give the including profile final precedence. An included profile may contribute defaults or an override for a check that is supplied by another profile; policy metadata is not conditional on that included profile placing the check in one of its own sections. The resulting policies must be the ones observed when the check actually runs.

A compiled profile must contain each check ID at most once, even if separate includes or the local profile list it under different section names. Keep the first occurrence and its section position according to the depth-first traversal above; later duplicates must not execute again. Reject direct or indirect include cycles with `ValueError` before recursion overflows, and include the profile-name chain in the error so the cycle can be diagnosed.

Finally, treat compilation as a snapshot. Nested configuration-default and override structures in a returned profile must not alias the source module's `PROFILE` data or another compilation result: changes on either side after compilation must not leak across that boundary. Preserve the existing public usage in which a custom module is passed to `profile_factory`, bundled profiles are referenced by short name, and profile/runtime exclusion and explicit-selection filters remain supported.
