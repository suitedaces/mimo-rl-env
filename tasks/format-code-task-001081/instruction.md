The docstring scraper in `doc/sphinxext/docscrape.py` is used by the documentation tooling to turn Numpy-style docstrings into structured data and rendered text. It currently treats some standard parameter-like sections as unknown or stores them as raw lines, so generator functions and APIs with optional tuning arguments lose information before the documentation is emitted. Complete this public parser contract while preserving the behavior of existing sections and wrappers.

`NumpyDocString` must expose `Other Parameters`, `Yields`, and `Warns` as section values using the same list-of-tuples representation as `Parameters`, `Returns`, and `Raises`: each entry is `(name, type, description_lines)`, with continuation lines and paragraph-separating blank lines retained in `description_lines`; an entry with no description has an empty list. Section headings should continue to be recognized through the parser's existing case/spacing normalization, and a docstring that omits any of these sections must still provide an empty list for each public key.

The normal string representation must emit these sections instead of dropping them, using the established parameter-list formatting and a stable semantic order: `Parameters`, `Other Parameters`, `Returns`, `Yields`, `Raises`, then `Warns`, followed by the pre-existing free-form sections. `FunctionDoc` and `ClassDoc` must inherit the same parsed values and rendered sections without losing their existing callable/class directive behavior. Existing handling and output for already-supported sections, signatures, and See Also/other free-form content must remain compatible.
