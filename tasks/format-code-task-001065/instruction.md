The learning-rate scheduler utility needs to remain usable with the PyTorch versions supported by this checkout while making its boundary behavior explicit. At present, constructing CosineWarmupScheduler can fail because the underlying LambdaLR API no longer accepts the legacy verbose keyword, and the warmup/decay arithmetic has undefined cases when warmup is disabled or the configured horizon is inconsistent.

Keep the existing public constructor and cosine_schedule entry points. CosineWarmupScheduler must accept the existing verbose argument on the installed PyTorch version (it may be a compatibility no-op), remain usable as a LambdaLR scheduler, and continue to support multiple optimizer parameter groups. Reject a negative warmup_epochs, a max_epochs less than one, or a warmup_epochs greater than max_epochs with ValueError before scheduling begins.

For a positive warmup, epochs before the warmup boundary must scale each parameter group's original learning rate linearly by (epoch + 1) / warmup_epochs. Once warmup is complete, the schedule must begin at start_value and follow cosine_schedule to reach end_value at max_epochs; stepping at or beyond the horizon must remain at end_value. A zero-length warmup is valid: it skips the linear phase and starts directly with the cosine schedule without division-by-zero or a discontinuity. Scaling must be relative to each group's own base learning rate rather than replacing group-specific rates. Saving and restoring the scheduler through the standard state_dict/load_state_dict API must preserve the current epoch and produce the same subsequent learning rates as an uninterrupted scheduler.

cosine_schedule itself must retain its existing validation and warning behavior, and when step exceeds max_steps it must emit RuntimeWarning while returning the terminal end_value. Existing valid calls and optimizer stepping order must continue to work.
