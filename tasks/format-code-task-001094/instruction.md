The storage layer behind SearchIndex.load/fetch should be safe for streaming ingestion and consistent between the hash and JSON backends. Update the public HashStorage and JsonStorage bulk methods so callers can pass ordinary sequences or one-shot iterables such as generators without the implementation probing them with len() or consuming them out of order. Synchronous write/get and asynchronous awrite/aget must preserve the order of the supplied objects or keys in their returned lists.

Bulk writes must keep the existing id_field/key construction and backend persistence behavior, honor a positive write batch_size, and return an empty list for empty input while leaving the backend unchanged. If explicit keys are supplied, their count must match the objects and the mismatch must be rejected before anything is written. Keys passed to reads must be strings; malformed key items are rejected rather than sent to Redis. Synchronous batch_size values must be positive integers, and asynchronous concurrency values must be positive; invalid values are rejected deterministically.

TTL handling is part of the same contract: when supplied, every non-negative integer is forwarded to the backend including zero (Redis's immediate-expiration value), and negative or non-integer TTLs are rejected. These rules apply to both HashStorage and JsonStorage and to both sync and async writes. Existing key formatting and backend persistence behavior should remain compatible.
