`sam remote invoke` can invoke Lambda functions and Step Functions, send SQS messages, and put Kinesis records, but it cannot publish to an SNS topic. Add SNS topics as a first-class remote-invoke resource so the same command can be used to exercise notification paths in a deployed application.

An `AWS::SNS::Topic` must be discoverable by logical ID in a named CloudFormation stack and directly from an SNS ARN. For a direct ARN, retain the complete ARN as the topic's physical identifier. A stack whose only invokable resource is an SNS topic should select it automatically. Add SNS after the existing Lambda, Step Functions, SQS, and Kinesis resource precedence: introducing a topic must not displace the resource that an otherwise identical mixed stack selects today. Existing remote-invoke support for all four current resource types must continue to work.

Publishing must use the resolved topic ARN and the event payload as the SNS `TopicArn` and `Message`. User-supplied `TopicArn` and `Message` parameters must not override those command-owned values. When no event payload is supplied, publish `{}`. Forward other `--parameter` values to SNS, including ordinary string parameters such as `Subject` and `MessageStructure`. `MessageAttributes` is entered on the CLI as JSON text and must be decoded to the object expected by the SNS Publish API; malformed JSON must fail with the remote-invoke invalid-parameter error rather than reaching SNS.

Keep output consistent with the other remote-invoke backends. Text output is a JSON-formatted object containing only the returned `MessageId`. JSON output contains the complete SNS Publish response, including optional FIFO fields and response metadata. Translate botocore parameter-validation failures to the existing invalid-resource-parameter exception and SNS client failures to the existing remote-invoke API-call exception, so the command's normal user-error handling remains effective.
