I want the Python client to support creating custom Ollama models and uploading model file blobs through the public client API. A synchronous user should be able to call `Client.create(model: str, quantize: str | None = None, from_: str | None = None, files: dict[str, str] | None = None, adapters: dict[str, str] | None = None, template: str | None = None, license: str | list[str] | None = None, system: str | None = None, parameters: Mapping[str, Any] | Options | None = None, messages: Sequence[Mapping[str, Any] | Message] | None = None, *, stream: bool = False) -> ProgressResponse | Iterator[ProgressResponse]`. An asynchronous user should be able to call the same signature on `AsyncClient.create(...)`, returning either a `ProgressResponse` or an async iterator of `ProgressResponse` values.

When I call `client.create('dummy', from_='llama2')`, the client should send a POST request to `/api/create` with JSON `{'model': 'dummy', 'from': 'llama2', 'stream': False}` and return the server's progress/status response, for example a response body `{'status': 'success'}` should produce an object whose `status` is `success`. When I pass creation options like `quantize='q4_k_m'`, `adapters={'adapter.gguf': 'sha256:...'}`, `template='...'`, `license='MIT'` or a list of licenses, `system='...'`, `parameters={'stop': ['</s>']}`, and chat `messages`, those values should be serialized into the `/api/create` JSON body with `from_` renamed to `from` and fields whose value is `None` omitted. With `stream=True`, `Client.create(...)` should return an iterator over progress chunks from the create response, and `AsyncClient.create(...)` should return an async iterator over the same progress chunks.

I also need `Client.create_blob(path: str | Path) -> str` and `AsyncClient.create_blob(path: str | Path) -> str` for local model files. For an empty file, `create_blob` should compute and return `sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`, and it should upload the file bytes with a POST to `/api/blobs/<that digest>`. The blob upload should return the digest for both newly accepted uploads and already-existing blobs, as long as the server responds successfully. If the local path cannot be opened, the call should fail with the normal file-opening exception instead of inventing a digest. The module-level convenience API should expose `ollama.create` with the same behavior as the default synchronous client.
