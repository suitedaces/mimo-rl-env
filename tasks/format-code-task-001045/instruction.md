The notification API currently lets an authenticated member list their notifications, but clients cannot perform the common bulk action of clearing the unread badge. Add a write endpoint at `POST /api/notifications/mark-read/` and extend the existing notification-list response so clients can implement that workflow without racing a stale cache. The endpoint is authenticated and always operates only on notifications belonging to the authenticated user. It accepts exactly one of two JSON request shapes: `{"ids": [positive integer notification IDs]}` for a non-empty list, or `{"all": true}`. Reject a missing selector, an empty list, the wrong JSON type, non-positive/non-integer IDs, or a request that supplies both selectors with HTTP 400; unknown IDs and IDs owned by another user are ignored rather than treated as errors. For an accepted request, mark only matching unread notifications as read, leave already-read rows unchanged, and return HTTP 200 with the exact JSON object `{"updated": N}`, where N is the number of rows changed; repeating the same request is therefore successful and reports zero when nothing remains unread. The `all` form marks every unread notification of the current user and no one else's. The existing list endpoint keeps its DRF pagination/filtering envelope and gains an integer `unread_count` field that counts all unread notifications for the current user regardless of the list's `is_read`, search, type, ordering, or page parameters. Both the new write and existing notification saves/deletes must invalidate any cached list result so a subsequent GET reflects the changed state and count. Unauthenticated callers receive the API's normal HTTP 401 response.
