Interactive search mode should treat filter spelling consistently with the search parser. At present, parser validation accepts filter names without regard to case, but the interactive conversion and filter classifiers retain the user's raw spelling, so inputs such as `CASE:yes`, `RePo:...`, or `-F:...` can become non-canonical state, fail singular-filter handling, or lose their negation. Bring the public filter helpers and `convertPlainTextToInteractiveQuery` into one normalization contract.

Recognized canonical filter names and their documented aliases must be resolved case-insensitively. Negated names and aliases must resolve to the canonical positive `FilterType` while setting `negated` to true. Interactive state must preserve the exact value substring from the original query and mark converted entries non-editable. Singular filters must occupy one canonical key; when the query contains the same singular filter more than once using different case or spelling, the later occurrence wins. Repeatable filters must remain separate entries even when one occurrence uses an alias, and every such entry must still carry the canonical type. The finite/text classifier helpers must make the same case-insensitive decision. Invalid or unknown filters must continue to be left verbatim in `navbarQuery` and must not create filter state. Existing lowercase names, values, and non-negated behavior must remain compatible.
