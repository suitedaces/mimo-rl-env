The redirect table in h/redirects is consulted by the redirect tween before a request reaches the application. It is used for both old application routes and content migrations, but two details make it unsafe for real links: prefix rules can redirect an unrelated path that merely shares the same characters, and redirects currently discard the query string that callers supplied. In addition, a comment indented for readability is parsed as a rule and can prevent the application from booting.

Make redirect parsing and lookup behave like a reliable URL migration layer. The existing four rule kinds (exact, prefix, internal-exact, and internal-prefix) and declaration-order priority remain part of the interface. Parsing must ignore blank lines and comments after optional leading whitespace, while retaining the complete destination field (including its own query or fragment).

For lookup, an exact rule matches only its complete source path. A prefix rule matches the source path itself or a descendant whose next character is '/', but must not match a longer path segment such as /legacy-archive. Prefix redirects append the unmatched path suffix to the destination. Both external URLs and URLs produced by internal route names must carry the incoming request query string unchanged. If the destination already has a query, join the two query strings with '&'; if it has a fragment, insert the request query before that fragment. Do not add a dangling '?' when the request has no query, and preserve repeated or percent-encoded parameters.

The redirect tween must continue to return a 301 response and short-circuit the downstream handler for the first matching rule, while passing non-matching requests through unchanged. Keep malformed rule and unknown-type errors explicit rather than silently accepting invalid configuration.
