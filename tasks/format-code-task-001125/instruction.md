The downloader compression middleware needs to handle real HTTP Content-Encoding headers without losing data or metadata. At present it treats a comma-separated header such as "gzip, deflate" as one token, so a response can remain encoded while its header is removed; it also does not consistently account for repeated header values or the changed body length.

Extend the public behavior of HttpCompressionMiddleware.process_response. For non-HEAD Response objects, parse Content-Encoding case-insensitively, ignoring surrounding whitespace, whether codings arrive in one comma-separated field or as repeated header values. Content codings are listed in wire order, so decode supported gzip, x-gzip, and deflate layers from the outside inward (the rightmost coding first), including all consecutive supported layers. If the outermost remaining coding is unsupported, leave the response body and compression metadata unchanged. If supported outer layers can be removed before an unsupported inner coding is reached, decode those layers and retain the unsupported coding in its original order. Once every coding has been removed, remove Content-Encoding; whenever a Content-Length header was present and decoding changed the body, rewrite it to the decoded byte length.

After decoding, the returned response must be classified from the now-decompressed headers/body so an HTML response is usable as HtmlResponse/TextResponse as appropriate. Preserve the request association, flags, and response metadata while creating the decoded response. Keep existing safeguards and compatibility: HEAD requests, non-Response values, and responses identified as intrinsically gzip content (the existing application/x-gzip or octet-stream guard) must pass through without decoding or header mutation. Malformed supported payloads should continue to surface the decoder failure rather than being silently accepted.
