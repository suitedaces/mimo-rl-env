The table-routing utilities expose the same routing rule model through two public implementations: util/table-router for glob-style rules and util/regexpr-router for mixed glob/regular-expression rules. In case-insensitive mode, Route already treats schema and table names without regard to ASCII case, but FetchExtendColumn can fail to find the selected rule or can return empty captures when the incoming names use different casing. The constructors also currently normalize the caller's TableRule objects in place, which makes a configuration object change merely because it was installed in a router.

Make case-insensitive routing and extraction consistent in both implementations. NewTableRouter(false, ...) and NewRegExprRouter(false, ...) must match schema/table patterns regardless of input case, and FetchExtendColumn must use the same matched rule that Route would use: a table-level rule takes precedence over a matching schema-level fallback. All configured extractors (table, schema, and source) must work under this case-insensitive matching mode, while capture values come from the original caller strings and therefore preserve their spelling. A rule that does not match must still produce empty column and value slices.

Do not mutate the TableRule values supplied to either constructor while preparing case-insensitive matching; their pattern fields remain as the caller provided them. Case-sensitive routers (the true mode) retain their existing exact-case behavior and existing target/default semantics. Keep the public method signatures and the existing error behavior for invalid or ambiguous rules.
