Make Koa's proxy support safe for applications that sit behind a known chain of reverse proxies. Today `app.proxy` is only an all-or-nothing boolean, so enabling it trusts every value in `X-Forwarded-For`, including values a client may have inserted before the first proxy controlled by the application.

Keep the existing `app.proxy = false` and `app.proxy = true` modes, and additionally allow `app.proxy` to be a trust predicate with the signature `function (address, hop)`. A truthy result means that hop is trusted. The socket's `remoteAddress` is hop 0. For `X-Forwarded-For`, trim comma-separated entries and ignore empty entries, then walk from the rightmost (nearest) forwarded address toward the left. Before accepting the next address, evaluate the current sender with its hop number. Stop when the current sender is untrusted. The first untrusted forwarded address is therefore retained as the client boundary, but addresses to its left are not. Return accepted forwarded addresses from `request.ips` in their original client-to-proxy order, without adding the socket address. For example, with socket `10.0.0.3`, header `198.51.100.7, 203.0.113.9, 10.0.0.2`, and a policy that trusts hops `10.0.0.3` and `10.0.0.2`, `ips` is `['203.0.113.9', '10.0.0.2']` and `ip` is `'203.0.113.9'`. `request.ip` must continue to use the first accepted forwarded address, falling back to the socket address and then `''`.

Forwarded host and protocol are single-value decisions: when a predicate is configured, use `X-Forwarded-Host` and `X-Forwarded-Proto` only if the direct peer at hop 0 is trusted, taking the first comma-separated value as Koa does today. Otherwise use `Host` and the connection protocol. A TLS socket always reports `https`, even if the peer is untrusted or a forwarded header says `http`; an unencrypted request with no usable trusted forwarded protocol reports `http`. If a predicate is configured but the socket has no `remoteAddress`, no forwarded field is authorized.

Boolean compatibility is part of the contract: `true` still trusts the complete non-empty forwarded IP list plus the first forwarded host/protocol values, while `false` ignores all forwarded fields. The derived public properties `hostname`, `origin`, and `secure`, and the corresponding context aliases, must reflect the same trusted host and protocol decisions.
