Glazier's configuration builder recursively expands includes and templates while mutating BuildInfo's active path. Today a malformed manifest can leak raw Python exceptions, a recursive reference can run until recursion failure, a failed include can leave the path stack corrupted, and a ChangeServer restart can retain tasks from the abandoned server. That makes both validation tools and a real imaging restart unreliable.

Make ConfigBuilder.Start a safe, reusable compilation boundary with these observable rules:

- Add public ConfigCycleError and InvalidConfigError exception types in glazier.lib.config.builder. InvalidConfigError is used for structural manifest errors and its message names the configuration file that contains the invalid value.
- A loaded document must be a mapping with a controls list. Each control must be a mapping. If templates is present it must be a mapping, and a template body must be a control mapping when expanded. An include value must be a list of two-string [path, filename] entries. A template value must be a list of strings, and every referenced name must exist in that document's templates. Violations raise InvalidConfigError rather than KeyError, TypeError, or an incidental action error.
- Detect recursion in both include expansion and template expansion. Include identity is the resolved configuration path after normalizing slash-delimited "." and ".." components, so an include such as sub/child.yaml -> ../build.yaml is a cycle. ConfigCycleError messages must contain the word "cycle" and show an ordered, closed chain (the repeated item appears at both ends); template-cycle messages must also identify the chain as templates. Detection is active-stack based: including the same file again after the first visit has returned is legal and expands it again.
- Preserve successful compilation compatibility. Expansion remains depth-first at the include position. Every file visit is wrapped by its existing SetTimer entries named start_<path>_<filename> and stop_<path>_<filename>, and emitted tasks retain the active path and server for that visit.
- Compilation is transactional with respect to its output and traversal state. If any read, validation, action, or cycle error escapes Start, do not create or replace the output task list. On every return or exception, restore ActiveConfigPath exactly to the value it had on entry; do not simply clear caller-owned components. The same ConfigBuilder instance must be usable for a later successful Start after a failure.
- ChangeServer's documented second string argument is a slash-delimited configuration root. Normalize leading and trailing separators into path components rather than treating the string as an iterable of characters. When the realtime action requests a restart, discard every task and timer from the abandoned attempt and compile build.yaml afresh from the new server/root. The replacement output must contain only the new attempt's tasks with its new server and normalized path context. After success, keep the new ConfigServer value but restore ActiveConfigPath to its pre-Start value.
