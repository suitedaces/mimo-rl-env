The Swarm data-resource layer is incomplete. `docker.config` is currently only a placeholder, while `docker.secret.create` forces callers to put payloads in a temporary file. This makes generated configuration and secret material awkward to use and leaves the two immutable Swarm resources with inconsistent Python behavior. Add a first-class config API and make secrets accept either a path or an in-memory payload without breaking existing callers.

`DockerClient.config` and `DockerClient.secret` must expose `create`, `inspect`, `list`, and `remove`. `create` takes a resource name and exactly one payload source: `file` (a path-like value) or `data` (bytes or text). Text is encoded as UTF-8; bytes, including NUL and non-UTF-8 bytes, are passed unchanged; an explicitly supplied empty value is still a payload. Supplying neither source or both must raise `ValueError` before invoking Docker. Keep the existing positional `secret.create(name, file, driver, labels, template_driver)` form working. Config creation supports `labels` and `template_driver`; secret creation additionally supports `driver`. Each label is sent as a separate `--label key=value`, and only supplied optional flags are sent. File sources are passed to Docker as paths; in-memory sources use `-` on stdin. The create methods return the corresponding resource object identified by Docker's returned ID.

The returned objects and objects from `inspect` must lazily reload through Docker's inspect JSON and expose `id`, `version`, `created_at`, `updated_at`, and a `spec` object. `spec.name`, `spec.labels`, and the Docker base64 `spec.data` value are available for both resources. A present `Spec.Templating.Name` is available as `spec.templating.name`; a present secret `Spec.Driver.Name` is available as `spec.driver.name`. Missing optional sections are represented as `None` (or an empty labels mapping), rather than making otherwise valid inspect output unparsable. `inspect` accepts either one name/ID or a list and returns the matching object or list.

`list(filters=...)` must pass each filter as a repeated `--filter key=value` and return immutable-ID objects for the IDs Docker prints, including an empty result. `remove` accepts a name/ID, a resource object, or a list containing either. Resource objects support `remove()` and context-manager cleanup: leaving a `with` block removes the resource even when the block raises.
