Compose instance launches depend on `ServiceGroup.PrioritySort`, but that boundary currently behaves differently from `ServiceGroup.Valid`: malformed groups can panic or reach the planner, cyclic graphs can produce an apparent launch order, and unrelated services are ordered by Go map iteration. Harden these two public APIs so a launch plan is validated, deterministic, and safe to consume.

A service group is launchable only when it is non-nil and non-empty. Keep the existing rejection of empty or hyphenated service names. Every map value, its embedded compose `Service`, and its Swan `Extra` settings must be non-nil. The map key, `DockerService.Name`, and embedded `ServiceConfig.Name` must all be the same non-empty service name. A well-formed single-service group remains valid. Malformed-member errors from both public APIs must identify the offending map key when one exists, and neither API may panic for malformed input.

Validate dependency declarations as part of the same contract. Every `DependsOn` name must exist in the group, and a service may neither depend on itself nor list the same dependency more than once. `PrioritySort` must apply the same acceptance rules as `Valid`; for any invalid group it returns a non-nil error and a nil order, never a partial plan. Its dependency-declaration diagnostics must identify the service and dependency involved.

For a valid acyclic group, `PrioritySort` returns every service exactly once after all of its direct and transitive dependencies. Whenever several services are currently eligible, choose the lexicographically smaller service name first. The result therefore must not depend on map iteration order or the order of equivalent names in `DependsOn`, and repeated calls must return the same slice contents. Planning must not reorder or otherwise mutate caller-owned `DependsOn` slices.

Reject self-cycles and multi-service cycles through both `Valid` and `PrioritySort`. `PrioritySort` must return a nil order with its error, even when an acyclic component could otherwise be planned, and its cycle diagnostic must include every service name in the detected cycle. No exact error wording is required beyond the identifying names described above.
