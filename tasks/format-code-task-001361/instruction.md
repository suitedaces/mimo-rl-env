I want the Go `config.Notifier` created with `config.NewNotifier(ec *config.EngineConfig)` to rate-limit large vserver changes before it sends cluster configuration updates on its `C` notification channel. On the initial notification from `NewNotifier`, if the loaded cluster contains more than 10 vservers, the notification should expose only 10 of them in `Notification.Cluster.Vservers` so the engine does not apply a large creation burst at startup.

For later reloads, when `Notifier.Reload()` causes a config update, unchanged vservers should always remain present in the emitted `Notification.Cluster.Vservers`. If a reload only adds vservers and more than 10 are new, the notification should include all unchanged vservers plus only 10 of the new vservers. For example, moving from `vs-01..vs-03` to `vs-01..vs-14` should emit 13 vservers total: the 3 unchanged ones and 10 additions.

If a reload deletes vservers, deletion limiting should take priority over additions. The notification should preserve all vservers that still exist in the new config, remove at most 10 deleted vservers from the emitted map, and keep any remaining deleted vservers for a later notification. For example, moving from 11 configured vservers to none should emit 1 remaining vserver, representing that only 10 deletions were allowed in that notification. This behavior should apply through the notifier lifecycle and should not require callers to manipulate the vserver map themselves.
