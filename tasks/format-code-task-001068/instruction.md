Incident escalation is currently difficult to reason about and impossible to replay: calendar lookups silently depend on wall-clock time, policy rules are read in database order, malformed event titles can abort a whole lookup, and notification generation ignores the policy repeat count while anchoring sends to the planner's current time. Make the escalation and notification helpers produce a deterministic, robust plan for each incident.

Extend the public `get_escalation_for_service(service, at=None)` helper with an optional evaluation timestamp. When `at` is supplied, a calendar event is active exactly when `event.start <= at <= event.end`; events outside that closed interval must not contribute. Rules must be evaluated by ascending `SchedulePolicyRule.position`, and a fixed user contributes at that position just like a calendar rule. Calendar event titles contain comma-separated usernames: trim whitespace, ignore blank or unknown names, and emit each user at most once while preserving first-seen policy/title order. A service without a policy returns no recipients. Existing one-argument callers remain valid and use the current time.

Update incident notification planning so `NotificationHelper.generate_notifications_for_incident(incident)` uses `incident.occurred_at` as its schedule anchor and the recipient snapshot at that same instant. For each complete ordered recipient pass, create notifications in recipient order and each user's notification-method `position` order. The first method of the first recipient is at the anchor; subsequent methods add `service.retry` minutes, and the next recipient starts after `service.escalate_after` minutes. A method exactly at the next recipient boundary is excluded, while a zero retry interval keeps all methods at that recipient's start. Repeat the complete recipient pass exactly `policy.repeat_times` times; non-positive repeat counts produce an empty plan.
