Scanner V4's HTTP client must consistently recognize in-cluster Central and Sensor service URLs when the pod runs in an arbitrary namespace. Today the transport mux compares only one exact host spelling, so ordinary Kubernetes DNS variants can silently bypass the service-specific mTLS transport or the deny policy. Make service classification robust while preserving the existing public TransportMux and TransportOption APIs.

For the namespace supplied by POD_NAMESPACE, Central and Sensor requests must be classified by service identity, not by an incidental URL spelling. Accept the short service DNS name (central.<namespace> or sensor.<namespace>), the .svc form, and the fully-qualified .svc.cluster.local form, with an optional port, case-insensitively and with a single trailing DNS dot. Every accepted spelling must use that service's configured RoundTripper, so WithDenyStackRoxServices(true) rejects all of them rather than falling through to the default transport. WithDenyCentral and WithDenySensor remain independent: disabling one service's traffic must not disable the other service's accepted names.

Classification must remain strict. A different namespace, a service-name prefix/suffix, or a similarly named service is ordinary external traffic and must continue through the caller-provided default RoundTripper. Existing exact .svc routing and the default passthrough behavior must remain compatible. The implementation may choose any internal hostname parsing or matching strategy, but it must not require DNS lookups or network access.
