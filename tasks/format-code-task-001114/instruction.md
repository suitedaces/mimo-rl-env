The condition system is used both during change processing and by the single-rule verification endpoint, but its data contract is currently fragile: form-produced rows can be incomplete, text fields have existed under more than one name, and a malformed regular expression can abort an otherwise valid check. Make condition evaluation deterministic and tolerant while preserving the existing public function and plugin model.

`execute_ruleset_against_all_plugins(current_watch_uuid, application_datastruct, ephemeral_data)` must evaluate the complete rules in the selected watch and return the existing result object with `result` and `executed_data`. The text supplied as `ephemeral_data['text']` must be available to conditions through both `page_filtered_text` and the backwards-compatible `page_text` field, with the same value. The built-in `contains_regex` and `!contains_regex` operators remain case-insensitive.

Interpret `conditions_match_logic` case-insensitively: `ALL` requires every usable rule to pass and `ANY` requires at least one usable rule to pass. An unrecognized mode value must use the safe `ALL` behavior. A row is usable only when it has non-empty operator, field, and value; rows with missing keys or empty sentinel values are ignored rather than raising an exception. If no usable rows remain, the condition set passes (there is no constraint).

Invalid regular-expression syntax is a non-match for both regex operators, including the negated operator; it must produce a normal `result: false` response rather than leaking `re.error` or another exception. Numeric extraction must retain an extracted zero as `executed_data['extracted_number'] == 0.0`. When a later evaluation has no extractable price, it must not inherit a prior evaluation's numeric value: `extracted_number` is absent from that evaluation's data and a comparison against zero does not pass. Keep existing operators, plugin extensibility, and successful evaluations compatible with current callers.
