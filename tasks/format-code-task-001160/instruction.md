The protocol engine can command a Heater-Shaker to shake, but the command result and engine state do not expose the validated target speed. This makes clients unable to report whether shaking is active and causes later temperature commands to accidentally discard shaker state. Make shake speed a first-class part of the Heater-Shaker protocol-engine contract. A successful `heaterShaker/setAndWaitForShakeSpeed` must validate the requested RPM against the existing inclusive 200-3000 RPM range, round it to the integer sent to hardware, call hardware with that normalized value when hardware is attached, and return the normalized value in its result for both attached and virtual modules. A loaded Heater-Shaker starts with no target speed; the read-only module substate must expose the optional target and provide a getter that returns the speed or raises the dedicated no-target-speed error. Successful speed commands update that state, and `heaterShaker/deactivateShaker` clears only the speed. Setting or deactivating the heater must preserve the shaker target, and setting or deactivating the shaker must preserve the heater target. Existing validation behavior remains: boundary values are accepted, out-of-range values are rejected with `InvalidTargetSpeedError`, and normalization is integer rounding.
