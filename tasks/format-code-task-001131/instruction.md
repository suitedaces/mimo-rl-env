Sarama advertises support through Kafka 2.4, but its Metadata API codec and the metadata requests generated by clients stop at version 5. This prevents callers from observing partition leader epochs and Kafka's authorized-operation bitfields even when the configured broker version supports them. Complete Metadata API versions 6, 7, and 8 while preserving the older protocol behavior.

`MetadataRequest` versions 6 and 7 have the same body as version 5. Version 8 appends two independently controlled booleans after `AllowAutoTopicCreation`: expose them as public fields named `IncludeClusterAuthorizedOperations` and `IncludeTopicAuthorizedOperations`, in that wire order. Encoding and decoding must preserve either flag combination. Versions above 8 remain unsupported. The minimum Kafka versions are 2.0.0 for metadata v6, 2.1.0 for v7, and 2.3.0 for v8; sending one through `Broker.GetMetadata` against an older configured broker must return `ErrUnsupportedVersion`.

`MetadataResponse` version 6 retains the version 5 layout. Starting in version 7, every `PartitionMetadata` carries a public `LeaderEpoch int32` immediately after `Leader`; version 8 retains that field. Version 8 also carries a public `ClusterAuthorizedOperations int32` after `ControllerID`, and a public `TopicAuthorizedOperations int32` at the end of each `TopicMetadata`. These are opaque signed bitfields: preserve their exact values, including negative values, on decode and re-encode.

Metadata requests created internally by an ordinary client must select versions from `Config.Version` as follows: pre-0.10 uses v0, Kafka 0.10 and 0.11 use v1, Kafka 1.0 and 1.1 use v5, Kafka 2.0 uses v6, Kafka 2.1 and 2.2 use v7, and Kafka 2.3 and 2.4 use v8. `ClusterAdmin.DescribeTopics` and `ClusterAdmin.DescribeCluster` must use v5/v6/v7/v8 for configured Kafka 1.x/2.0/2.1-2.2/2.3-2.4 respectively. Internally generated v8 requests must leave both authorized-operation flags false; callers who construct a `MetadataRequest` directly can opt in through the public fields. Existing v0-v5 request encoding and the established v0, v1, and v5 response layouts must remain compatible.
