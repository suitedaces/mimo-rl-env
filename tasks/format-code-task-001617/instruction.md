Django's migration machinery treats model fields as value objects: it deconstructs them into constructor arguments, stores that state, and clones fields while comparing model state. TaggableManager is a field-like relationship, but its deconstruction currently forgets relationship-only options. A project using a custom through model or a reverse relation name can therefore have a field that behaves one way at runtime and another way after a migration state is reconstructed; repeated schema checks can also see a false difference because cloning silently falls back to the built-in generic through model.

Make TaggableManager's public deconstruct() and clone() behavior migration-safe and consistent with Django's field conventions. A custom through reference supplied as a dotted string must be emitted unchanged. When a through model class is supplied, emit its stable app-label/model-name reference, just as Django relationship fields do; after a lazy string reference has resolved to a model class, deconstruction must still emit that same reference. Include related_name whenever it was explicitly supplied, including an empty string, and omit it when it is unset. Preserve blank=True and the existing verbose_name/help_text values, while continuing to omit the runtime-only serialize and null constructor flags.

Calling clone() must recreate an equivalent manager: its through reference, reverse-name setting, blank flag, and presentation metadata must survive, and the clone must be a separate field whose relationship metadata can be changed without changing the original. Keep the default TaggableManager compact: an unconfigured manager should continue omitting through, related_name, and blank from deconstruction and a clone should use the built-in TaggedItem through model. The behavior must work both before and after Django contributes/resolves the field; do not require callers to edit generated migrations manually.
