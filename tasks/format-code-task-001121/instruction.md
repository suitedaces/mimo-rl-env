The `decode_json_fields` processor currently decodes only the selected field's top-level JSON object. This leaves structured log payloads partially opaque when a decoded object contains more JSON strings, and it is especially inconvenient for arrays of embedded records. Extend the processor so its existing configuration remains compatible while decoding nested values predictably. A selected string field is decoded as JSON and written using the existing `target` and `overwrite_keys` behavior. After each successful decode, nested object values that are strings containing valid JSON must also be decoded, recursively, until `max_depth` is exhausted; non-JSON strings remain unchanged and malformed nested values must not make the processor fail. The configured depth is a boundary: the root decode is depth one, the default remains one, and no value beyond the requested depth is decoded.

When `process_array` is enabled, apply the same recursive inspection to arrays at any nesting level, including object elements and string elements, while preserving scalar array elements and their order. When it is disabled, array contents are left at the current decoded representation even if an element looks like JSON. This option must not change object recursion. Numeric JSON values must retain the processor's existing number conversion behavior.

Preserve the public processor contract: missing or non-string selected fields are ignored as before; a non-empty `target` receives the decoded value without removing the source field; an empty `target` merges decoded object keys into the event root according to `overwrite_keys`; and decoding a JSON scalar into the root still reports an error rather than silently replacing the event. Keep the existing plugin name and configuration validation semantics.
