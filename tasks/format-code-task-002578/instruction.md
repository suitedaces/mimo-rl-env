I want an existing `DropboxClient` instance to expose cursor-based remote change polling and listing methods for code that keeps a Dropbox folder in sync: `wait_for_remote_changes(last_cursor: str, timeout: int = 40) -> bool`, `list_remote_changes_iterator(last_cursor: str) -> Iterator[ListFolderResult]`, and `list_remote_changes(last_cursor: str) -> ListFolderResult`.

`wait_for_remote_changes` should long-poll Dropbox for changes after the supplied cursor and return `True` when changes are available and `False` when the poll times out without changes. It should reject invalid timeouts outside the Dropbox long-poll range `[30, 480]` by raising `ValueError`. When Dropbox asks the client to back off, the same `DropboxClient` instance should remember that backoff and delay the next long-poll before sending it.

`list_remote_changes_iterator` should continue from a cursor and yield each page of remote changes as a Maestral `ListFolderResult`, preserving each page's cursor and converted metadata entries. If Dropbox reports more pages, iterating should keep following the returned cursor until all pages have been yielded. `list_remote_changes` should provide the convenience form: it consumes the iterator for the same cursor and returns one flattened `ListFolderResult` containing all entries from all pages, with the final cursor from the last page.

Dropbox API and connection failures from these methods should be converted into Maestral API exceptions in the same way as the rest of `DropboxClient`, so callers can handle remote-change polling and listing consistently with other client operations.
