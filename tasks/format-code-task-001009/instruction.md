Make the shared parseLinkHeader pagination utility robust enough for real HTTP Link headers. It is used throughout the frontend, but its current comma split and fixed-order regular expression lose valid links when a URL or quoted parameter contains a comma, and they only recognize one exact serialization of the pagination parameters.

Treat the input as a sequence of Link-style entries. A comma separates entries only when it is outside both the <...> link target and a quoted parameter value. Each usable entry has an angle-bracketed target followed by semicolon-delimited parameters. Allow optional spaces around commas, semicolons, and =, and accept the parameters in any order. Parameter names are ASCII case-insensitive. Both quoted-string and unquoted token values must work. Within a quoted string, a backslash quotes the following character and must be removed from the returned value.

rel remains the key used in the returned record. A space-separated rel value denotes multiple relations, and the same parsed pagination value must be available under every nonempty relation in that list. Each value has the existing public shape: href is the target text between < and > without URL resolution or decoding; cursor is the decoded parameter value when present and otherwise resolves to undefined; and results is true or false for those values case-insensitively, otherwise null (including when the parameter is absent).

Text entries without an angle-bracketed target and links without a rel parameter are ignored without discarding other usable entries. null, an empty string, or input containing no usable links returns an empty record. When later usable entries repeat a relation, the later entry wins. Relation names are not restricted to next and previous: names that coincide with JavaScript object properties, including __proto__ and constructor, must be returned as ordinary own keys rather than being interpreted through inherited properties or prototype setters.

Keep the established behavior for the common quoted next/previous form and for arbitrary single relation names while adding these more flexible forms.
