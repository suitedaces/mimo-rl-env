Typed resources built through the internal SDK cannot currently evolve persisted Terraform state: the wrapper exposes CRUD, import, update, diff, and deprecation capabilities, but it drops state-version metadata. That makes a typed resource unsafe to change when its stored schema needs a migration. Add an optional state-migration capability to typed resources and carry it through the existing ResourceWrapper into the Terraform Plugin SDK resource.

A typed resource opts in by exposing both `SchemaVersion() int` and `StateUpgrades() map[int]pluginsdk.StateUpgrade`. For an opted-in resource, `ResourceWrapper.Resource()` must publish the declared schema version and one Terraform state upgrader for every declared source version. Upgraders must be ordered by ascending source version, their `Version` fields must match those source versions, and each upgrader's protocol type must be derived from that version's `StateUpgrade.Schema()` snapshot rather than from the current resource schema or another migration.

Each published upgrader must invoke the `UpgradeFunc()` belonging to that same source version. It must pass through the caller's context, raw state, and metadata, return the migration's resulting state, and surface any migration error. Sequential migrations must therefore remain independent and be runnable in order; do not accidentally bind every protocol upgrader to the same map entry.

Treat the declaration as a versioned chain. `SchemaVersion` must be non-negative, and the upgrade map must contain exactly one non-nil entry for every integer source version from `0` through `SchemaVersion-1`, with no gaps or out-of-range entries. Version zero with no upgrades is valid. If an opted-in resource violates these rules, wrapper construction must return an error rather than panic or publish a partial chain. Typed resources that do not expose the migration capability must retain the current behavior: schema version zero, no state upgraders, and otherwise unchanged wrapping.
