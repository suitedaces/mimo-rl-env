I want the `*tbot.Client` returned by `NewClient(token, httpClient, baseURL)` to have a working shared Telegram Bot API request transport behind its public methods.

For form-only methods, the client should POST to `{baseURL}/bot{token}/{method}` using `application/x-www-form-urlencoded` data when parameters are present. For example, with a test HTTP server as `baseURL`, calling `GetMe()` and receiving `{"ok":true,"result":{"id":1,"is_bot":true,"first_name":"Bot"}}` should return a `*User` with `ID == 1` and no error. Calling `SendMessage("123", "hello")` and receiving `{"ok":true,"result":{"message_id":7,"chat":{"id":123},"text":"hello"}}` should return a `*Message` with `MessageID == 7`, `Text == "hello"`, and no error.

The transport should decode Telegram's response envelope for every call: when `ok` is true, unmarshal `result` into the typed return value; when `ok` is false, return a non-nil Go error whose text is Telegram's `description`, such as `Bad Request: chat not found`. If the HTTP request itself fails or the response body is not valid JSON in the expected envelope shape, the method should return a non-nil error rather than a partially decoded result.

For local upload methods such as `SendPhotoFile("123", "photo.jpg")`, the client should stream the named local file with a `multipart/form-data` POST to the same Bot API method endpoint, include ordinary form fields such as the chat id, and include the upload as a file part with the method's file field name and the original filename. A successful Telegram envelope should decode into the method's typed return value just like form-only calls. If the local file cannot be opened, or if the multipart upload receives a non-200 HTTP status, the method should return a non-nil error.
